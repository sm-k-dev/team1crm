# 팀 공통 프로젝트 관리

## 도구와 정보의 기준
- **GitHub Issues/Projects**: 작업 상태의 기준. 작업마다 Issue ID, 담당자, 완료 조건, 예상 마감일을 적는다.
- **Pull Request**: 구현 및 리뷰 증거. 코드가 커밋됐다는 사실만으로 작업 완료로 간주하지 않는다.
- **Google Sheets(공유)**: 프로젝트 요약, 일정, 위험·의사결정, 개인별 상세 업무일지, 금요일 주간 보고용. 실제 공유 문서는 아직 생성하지 않았다.
- 작업 상태 제안: `할 일 → 진행 중 → 리뷰 중 → 완료`, 별도 `막힘` 표시.
- 완료 기준 제안: 구현·테스트·PR 리뷰·CI 통과·병합 및 관련 문서 업데이트. 팀에서 확정한다.

## 일일 흐름
1. 아침 5분: 어제 완료, 오늘 계획, 막힌 점 공유.
2. 작업 시작: Issue 지정, 브랜치 생성, `진행 중`으로 변경.
3. 작업 종료: 커밋/PR 링크와 상세 업무일지를 작성한다(하루 여러 행 허용).
4. PR 병합 후: Issue 닫기, 상태 `완료` 반영.
5. 금요일: 팀 공통 주간 보고 작성. 강사 제출 양식과 대조한다.

## 중복 입력 방지
- 완료율은 **작업 목록의 상태**에서만 계산한다. 업무일지 행 수를 완료율로 계산하지 않는다.
- 개인 업무일지는 작업의 과정·문제·해결·학습을 기록하고, Issue/PR 링크로 공통 작업과 연결한다.
- 코드·키·DB 비밀번호·고객 개인정보는 업무일지에 붙여넣지 않는다.

## 회의에서 결정할 항목
- [ ] 일지 작성 마감 시점 및 주간 보고 담당
- [ ] 일정 지연·막힘 보고 기준
- [ ] 작업 완료 기준과 PR 주기
