# 네이밍·코드 포맷·메서드 설계 (팀 합의 초안)

> 범위: 모든 Java/Spring 프로젝트에 재사용. 강사 공지와 스타터의 기존 계약이 우선하며 기존 소스를 일괄 수정하지 않는다.

## 네이밍
| 대상 | 제안 | 예시 |
|---|---|---|
| 클래스/인터페이스/Enum | PascalCase | `CustomerService`, `PointType` |
| 메서드/변수 | camelCase, 의미가 드러나도록 | `calculatePointBalance`, `earnedPoints` |
| 상수/Enum 값 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT`, `EARN` |
| 패키지 | 소문자 | `service`, `repository` |
| boolean | 의미가 드러나는 긍정형 | `isActive`, `hasPermission` |
| 테스트 | 상황·기대 결과 표현 | `createCustomer_whenValid_succeeds` |

## 식별자 이름의 품사와 의미 (추가 제안)
> 아래 규칙은 **팀 논의용 제안**이다. 기존 코드·프레임워크 규칙과 충돌하면 팀에서 우선순위를 결정한다.

| 대상 | 권장 원칙 | 예시 |
|---|---|---|
| 클래스·인터페이스 | 역할을 나타내는 명사/명사구 | `CustomerService`, `CouponValidator` |
| 일반 메서드 | 수행 동작을 나타내는 동사로 시작 | `createCustomer()`, `calculatePointBalance()` |
| 변수·필드·매개변수 | 데이터 의미를 나타내는 명사/명사구 | `customerId`, `earnedPoints` |
| boolean 필드·메서드 | 참/거짓으로 읽히는 상태·질문 형태 | `isActive`, `hasPermission()`, `canRedeem()` |
| 상수 | 의미 있는 명사구, UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| 테스트 메서드 | 대상 동작·상황·기대 결과 | `createCustomer_whenValid_succeeds()` |

### 동사 선택과 일관성
- [제안] **동일한 동작에는 같은 동사를 사용**한다. 예: 삭제는 `deleteCustomer()`로 통일하고 `removeCustomer()`와 혼용하지 않는다.
- [제안] `create`는 신규 생성, `update`는 수정, `delete`는 삭제, `calculate`는 계산, `validate`는 검증에 사용한다.
- [제안] `find`는 결과가 없을 수 있는 조회에, `get`은 반드시 있어야 하는 대상을 가져오는 조회에 사용하는 방식을 고려한다. **Java의 강제 규칙은 아니므로** 반환 타입(`Optional` 등)과 실패 처리 방식까지 팀에서 합의한다.
- [제안] `list` 또는 `findAll`은 목록 조회에 사용하되, Spring Data Repository에서는 `findAll`, `findBy...`, `existsBy...` 등 **프레임워크의 쿼리 메서드 규칙을 우선**한다.
- [제안] `save`는 생성과 수정을 모두 포함할 수 있으므로, Service의 업무 의미를 분명히 해야 할 때는 `create`/`update`를 구분한다.
- [제안] 약어보다 뜻이 명확한 이름을 우선한다. 예: `getCustInfo()`보다 `getCustomerInfo()`.

### 계층별 메서드 예시
```java
// Controller: 페이지 표시(뷰 이름 반환)
@GetMapping("/customers")
public String showCustomerList() {
    return "customer/list";
}

// Service: 업무 동작(예시 시그니처)
public CustomerDto createCustomer(CustomerRequest request);
public CustomerDto getCustomer(Long customerId);
public void updateCustomer(Long customerId, CustomerRequest request);

// Repository: Spring Data의 파생 쿼리 메서드
Optional<Customer> findByEmail(String email);
boolean existsByEmail(String email);
List<Customer> findByStoreId(Long storeId);
```
- [제안] **REST URL은 자원(명사) 중심**으로 작성한다. 예: `GET /customers`. Java Controller 메서드는 `showCustomerList()`처럼 동사로 시작할 수 있다.
- [제안] `validateAndSaveCustomer()`처럼 여러 동작이 이름에 들어가면 책임 분리가 필요한지 검토한다. 단, 하나의 업무 흐름을 조정하는 상위 메서드라면 허용한다.
- [주의] 위 코드는 **네이밍 예시**이며, 실제 DTO·Entity·Repository의 존재나 구현 완료를 뜻하지 않는다.

## 작성·설계
- [제안] 메서드는 하나의 주요 책임을 맡고, 읽기 어려울 만큼 길어지면 의미 있는 단위로 분리한다.
- [제안] **30~50줄은 검토 신호일 뿐 강제 상한이 아니다.** 트랜잭션 경계나 가독성을 깨면서 무조건 쪼개지 않는다.
- [제안] 중첩 분기가 깊으면 조기 반환과 보조 메서드를 검토한다.
- [제안] 숫자·문자열의 업무적 의미가 중요하면 이름 있는 상수로 표현한다.
- [제안] 생성자 주입을 우선하고, Controller/Service/Repository의 기존 책임을 따른다.
- [제안] API·DB·인증 계약을 바꾸는 리팩터링은 사전 협의한다.
- [제안] IDE 자동 포맷으로 불필요하게 전체 파일을 바꾸지 않는다.

## 파일 네이밍 관련 안내
- 이 문서는 **소스코드 식별자·포맷·메서드 설계**를 다룬다. 파일명 날짜·버전 규칙은 `../docs/01_문서_네이밍_버전관리_규칙_초안.md`를 참조한다.
- Java 클래스 파일명은 클래스명에 맞춰 유지하며, `_YYYYMMDD_vN`을 붙이지 않는다.

## 팀 결정 필요
- 들여쓰기와 포맷터, import 정렬, 줄 길이, 메서드 분리 기준, DTO 네이밍 예외, 테스트 네이밍, 조회 메서드(`get`/`find`) 의미, Controller 화면 메서드 접두사(`show`/`render`), 삭제 동사(`delete`/`remove`) 통일.


## v1 패키지 네이밍 추가
- 최상위 도메인 패키지는 소문자 단수형: `auth`, `customer`, `loyalty`, `analytics`, `home`, `common`, `infrastructure`.
- `loyalty`만 기능별 하위 패키지 `visit`, `point`, `coupon`을 사용한다. `visit/service` 같은 추가 계층 패키지는 만들지 않는다.
- Controller/Service/Repository/Entity/DTO 클래스는 해당 기능 패키지 안에 둔다.
