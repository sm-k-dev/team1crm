# 문서 네이밍·버전 관리 규칙 (팀 합의 초안)

> 상태: [제안] — 팀원 검토 후 확정. 강사 지침 및 기존 프로젝트 계약이 우선한다.

## 1. 관리 대상 구분
- **소스코드** (`.java`, `.html`, `.css`, `.js` 등): 파일명에 날짜·버전을 붙이지 않고, Git Commit·Pull Request로 변경 이력을 관리한다. 주석은 역할·설계 의도·복잡한 로직·중요한 변경 이유를 설명한다. 주석이 Git 이력을 대체하지 않는다.
- **계속 갱신하는 공용 문서** (`README.md`, `docs/TEAM_GUIDE.md`, `docs/TODO_BY_ROLE.md` 등): 파일명을 고정하고 Git으로 변경 이력을 관리한다. 기존 링크를 유지한다.
- **개정판을 별도 보관하는 산출물** (설계서 검토본, 발표·제출용 문서 등): `파일명_YYYYMMDD_vN.확장자`를 사용한다.
- **회의록**: `회의록_YYYYMMDD.md`; 같은 날 여러 건이면 `_01`, `_02`를 덧붙인다.
- **DB 백업/스냅샷**: 필요 시 `crm_backup_YYYYMMDD_HHMM.sql`처럼 시각까지 표시한다. 비밀정보·개인정보·실제 데이터가 포함된 백업은 Git에 커밋하지 않는다.

## 2. 문서 버전 증가 원칙
1. `YYYYMMDD`는 해당 개정판 파일을 생성한 날짜다.
2. `vN`은 **동일 산출물에 대해 날짜와 무관하게 연속 증가**한다. 날짜가 바뀌어도 `v1`으로 초기화하지 않는다.
3. 동일한 날짜에 여러 개정판을 만들 수 있다.
4. Git에서 기존 문서를 단순 수정하는 경우 파일을 복제하거나 버전을 올릴 필요가 없다. **검토·제출 등 별도 개정판을 보관할 때만** 새 파일을 만든다.
5. `final`, `final2`, `최종진짜` 같은 모호한 접미사는 사용하지 않는다.

## 3. 예시
- `DB설계_20261104_v1.md` → `DB설계_20261104_v2.md` → `DB설계_20261105_v3.md`
- `API명세서_20261105_v1.pdf`
- `회의록_20261104.md`
- `crm_backup_20261104_1430.sql`

## 4. 코드 주석과 Git의 관계
- 클래스·메서드 JavaDoc의 작성자·최초 작성일·중요한 변경 설명은 `../coding/02_한국어_JavaDoc_작성자_날짜_규칙_초안.md`를 따른다.
- 커밋·PR은 누가 언제 무엇을 변경했는지 추적하는 공식 기록이다.
- 단순 수정마다 코드 파일명을 변경하거나 버전 주석을 추가하지 않는다.
