# Git 브랜치·커밋·PR 규칙 (팀 적용 제안)

> **상태:** 팀 검토용 제안. 실제 팀 합의 후 `TEAM_GUIDE.md`에 확정일을 기록합니다. Git은 커밋 메시지 형식을 강제하지 않으며 아래는 협업 규칙입니다.

## 커밋 메시지

```text
<type>(<scope>): <짧은 작업 요약>
```

- `type`: `feat` 기능, `fix` 버그, `refactor` 동작 유지 구조 개선, `docs` 문서, `test` 테스트, `style` 포맷만, `chore` 유지보수, `build` 빌드 설정, `ci` CI/CD, `perf` 성능, `revert` 되돌리기.
- `scope` (선택): `auth`, `admin`, `customer`, `loyalty`, `analytics`, `ui`, `db`, `deploy` 등. 실제 변경 영역을 사용합니다.
- 제목은 명령형 또는 완료형 중 팀에서 하나로 통일하며, 무엇을 변경했는지 구체적으로 작성합니다. 비밀번호·토큰·고객 개인정보는 포함하지 않습니다.
- 관련 업무 ID가 있으면 본문 또는 PR에 기재합니다. **업무관리 XLSX의 ID를 그대로 사용**하고 임의로 다시 번호를 붙이지 않습니다.

### 예시

```text
feat(loyalty): 방문 등록 입력값 검증 추가

Refs: B-001
```

```text
fix(auth): 정지된 OWNER의 API 접근 차단
```

```text
docs(ui): 방문·포인트·쿠폰 fragment 사용법 문서화
```

## 브랜치와 PR

- `main`: 리뷰 및 테스트를 통과한 통합 코드. 직접 push 대신 PR을 원칙으로 합니다(저장소 보호 규칙은 별도 설정 필요).
- 작업 브랜치 예: `feat/loyalty-visit`, `fix/auth-status`, `docs/commit-guide`.
- PR에는 변경 이유, 주요 변경 파일, 테스트 방법/결과, 영향받는 API·DB·화면, 관련 작업 ID를 기록합니다.
- 공통 보안·Entity·마이그레이션·공통 레이아웃 변경은 담당자 리뷰를 요청합니다.
- 기능을 구현하지 않았는데 `feat`로 완료를 주장하지 않습니다. 문서/스켈레톤만 추가했다면 `docs`/`chore`로 구분합니다.

## 배포 및 보안

- `.env`, 비밀키, 실제 고객정보, IDE 개인 설정 파일은 커밋하지 않습니다.
- DB 스키마 변경은 백업·마이그레이션·롤백 방안을 PR에 포함합니다.
- PR 승인만으로 자동 배포되지는 않습니다. CI/CD와 브랜치 보호 설정은 인프라 담당자가 별도 구성합니다.
