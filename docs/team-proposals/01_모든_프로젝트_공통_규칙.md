# 모든 프로젝트 공통 개발·협업 규칙

모든 항목은 **[제안]**이며, 강사 공지·스타터의 확정 요구와 충돌하면 해당 요구가 우선한다.

## 1. 소통과 담당 범위
- [제안] 매일 짧은 스탠드업: 어제 한 일/오늘 할 일/막힌 일.
- [제안] 30분 이상 막히면 이슈·채팅에 증상, 재현 방법, 시도한 내용을 남기고 도움 요청.
- [제안] 공통 파일(`SecurityConfig`, `application.properties`, 공통 레이아웃, DB 스키마, CI/CD)은 담당자에게 변경 사전 공유.
- [결정 필요] 팀 채팅·이슈 도구, 회의 시간, 긴급 연락 방식, 파일별 담당자.

## 2. Git·PR
- [강사/스타터 기준] `feature/* → develop → main`, PR 및 리뷰, CI 통과 후 병합. `main` 직접 푸시 금지.
- [제안] 한 PR은 한 목적만; 제목에 범위 표기 (`feat(customer): ...`).
- [제안] 커밋 메시지는 `feat|fix|refactor|test|docs|style|chore|ci: 설명`.
- [제안] 리뷰어 1명 이상, 공통 파일 변경은 관련 담당자 확인, PR 본문에 테스트 결과·화면 캡처(화면 변경 시)·영향 범위.
- [제안] 비밀키/DB 덤프/개인정보/IDE 설정 파일은 커밋하지 않음. `git add .` 전에 `git status`와 staged diff 확인.
- [결정 필요] 브랜치 이름 규칙, PR 크기, 승인자, squash/merge 정책, 긴급 수정 절차.

## 3. 코드·API 계약
- [제안] 스타터의 Java/패키지/레이어 구조를 따름. 독자적 프레임워크·라이브러리 추가 금지(별도 변경 승인 전).
- [제안] DTO·URL·HTTP 메서드·응답 코드·에러 형식은 호출자와 사전 협의. API 변경 시 사용하는 화면·테스트도 함께 점검.
- [제안] 컨트롤러는 요청·응답, 서비스는 업무 규칙, 리포지토리는 데이터 접근을 담당.
- [제안] 로그에는 비밀번호, JWT, API 키, 고객 전화번호 원문을 남기지 않음.
- [결정 필요] 코드 포맷, 주석 언어, null 처리, 예외 처리 공통 규칙, API 문서 업데이트 담당.

## 4. 인증·세션 계약
- [스타터 기준] 세션(`IF_REQUIRED`), JWT, Google OAuth2가 함께 존재. **세션 ID가 사용자마다 다른 것은 정상**.
- [제안] 로그인 사용자 식별 방식·세션 속성 이름·JWT 전달 헤더·권한 체크 경로는 임의로 바꾸지 않음. 변경 시 인증 담당자와 호출자 리뷰.
- [제안] 각자 별도의 인증 구현을 새로 만들지 않고 스타터 제공 구성요소를 재사용.
- [결정 필요] API와 Thymeleaf 화면의 인증 흐름별 테스트 책임자, 만료/로그아웃 동작 확인 방식.

## 5. 비밀정보·환경설정
- [스타터 기준] DB 계정, JWT_SECRET, OPENROUTER_API_KEY 등은 환경 변수로 제공 가능.
- [제안] 서버 공통 API 키를 Java 소스, 추적되는 properties, 일반 DB 테이블에 임의 저장하지 않음. 각 개발자 로컬 환경 변수와 배포 서버 설정을 사용.
- [제안] `.env.example` 등에는 변수 이름과 가짜 값만. 노출되면 키 폐기·재발급, Git 이력/로그 확인, 담당자 공유.
- [제안] 환경별 DB 초기화 옵션은 배포 전 별도 점검. 실제 고객 데이터 사용 금지.
- [결정 필요] 키 발급·보관 담당자, 로컬 공유 방법(키 원문을 채팅에 붙이지 않기), 서버 배포 권한.

## 6. DB·테스트·배포
- [제안] 엔티티/테이블/컬럼 변경은 사용 중인 담당자에게 사전 공지하고 데이터 영향·롤백 방법 기록.
- [제안] PR 전 `./gradlew clean build` 실행 및 기능별 최소 정상/실패/권한 테스트.
- [제안] 배포는 CI/CD 성공 후 진행하고 시연용 DB는 백업·초기화 여부를 명확히 관리.
- [결정 필요] 로컬 DB 데이터 생성 방법, 배포 승인 담당, 버그 우선순위, 완료 정의(DoD).

## 7. 완료 정의(DoD) 제안
- 요구사항 충족, 코드 리뷰 승인, CI 통과, 관련 테스트 수행, 개인정보/권한 검토, API·화면 문서 갱신, 변경 기록 완료.

## 8. 코딩 컨벤션 상세 초안 (신규)
- [제안] `common/coding/02_네이밍_포맷_메서드_설계_초안.md` 참조: 이름·포맷·메서드 책임과 분리 기준.
- [팀 제안] `common/coding/03_주석_작성자_날짜_규칙_초안.md` 참조: 한국어 설명, 모든 직접 작성 클래스/메서드의 역할·작성자·날짜.
- [결정 필요] 예외 범위, 최초 작성일 기준, 중요한 변경 기록 방식.

## 9. 파일명·문서 버전 관리
- [제안] 소스코드 파일명은 고정하고 변경 이력은 Git·PR로 관리한다. 코드 주석은 설명과 중요한 변경 이유를 기록한다.
- [제안] 개정판으로 별도 보관하는 문서에 한해 `파일명_YYYYMMDD_vN.확장자`를 사용하고 버전은 날짜와 관계없이 연속 증가시킨다.
- [제안] `README.md`, `TEAM_GUIDE.md`, `TODO_BY_ROLE.md` 같은 공용 문서는 파일명을 고정한다.
- **상세 기준:** `common/docs/01_문서_네이밍_버전관리_규칙_초안.md` (중복 정의하지 않고 이 문서를 기준으로 한다).


## v1 아키텍처 적용 기준 (확정된 구조)
- 단일 Spring Boot 애플리케이션에서 도메인별 패키지로 병렬 개발한다. 상세: `../architecture/01_프로젝트_패키지_구조.md`.
- `loyalty`는 `visit`, `point`, `coupon`까지만 하위 패키지를 둔다. 각 폴더에 관련 Controller/Service/Repository/Entity/DTO를 함께 둔다.
- 다른 도메인의 Repository 직접 호출은 지양하고 합의된 Service/조회 계약을 사용한다. 도메인 간 변경은 소유자 리뷰를 받는다.
- 인증, DB 스키마, 공통 CSS/레이아웃, CI/CD, build.gradle은 관련 소유자 사전 협의 후 변경한다.
