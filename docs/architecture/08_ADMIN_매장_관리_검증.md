# ADMIN 매장 관리 구현 및 로컬 검증 기록

## ADMIN 대시보드 후속 검증 (2026-11-11)
- 사장님 계정 이름 수정 후 동일 이메일·비밀번호로 로그인하고 새 이름 표시 및 매장 900107의 고객 관리 접근 유지까지 사용자 화면으로 확인했다.
- ADMIN 운영 대시보드를 실제 DB 집계와 연결했다. 한국 날짜 기준 이번 달 및 최근 6개월 등록 수를 조회하고 빈 월은 0을 표시한다. 매장 연결률은 중복을 제거한 매장 보유 USER 수 / 전체 USER 수이며 0명일 때는 0%이다.
- 사용자 브라우저에서 전체 사장님 5명 / 매장 4개 / 연결 4명 / 미연결 1명 / 연결률 80.0%, 미연결 hello 계정 표시를 확인했다.
- 월별 표의 10월 3명·3개, 11월 2명·1개와 전월 대비 -1명·-2개 표시가 서로 일치함을 확인했다. 월별 수치의 독립 SQL 대조는 별도이다.
- 현재 계정 900006의 이름은 관리자수정사장님이며 테스트 매장 900107의 소유자이다. 아래 기록의 이전 이름·소유자 상태는 각 검증 시점의 이력이다.

작성자: 김순민 / 검증일: 2026-11-11

기록 근거: 사용자 실행 결과와 공유한 브라우저·MySQL Workbench·오류 로그.

## 구현 범위

- ADMIN의 전체 매장 조회, 매장 등록·수정, 기존 사장님 연결 및 소유자 변경.
- 매장명·업종·주소·적립률 표시 및 입력 검증, 성공 시 목록으로 리다이렉트, 오류 시 입력값 유지.
- 현 구현에서 사장님 역할은 USER이다. ADMIN 및 존재하지 않는 회원을 매장 소유자로 지정하지 않는다.
- 사장님 한 명이 여러 매장을 소유할 수 있다. 연결된 사장님 수는 회원 ID의 중복을 제거해서 센다.
- 승인·반려·정지 상태 관리와 신규 사장님 계정 생성은 이번 구현 범위가 아니다.

## 기존 DB 유니크 제약으로 인한 등록 실패

### 증상과 원인

기존 사장님에게 두 번째 매장을 등록할 때 오류 화면이 표시됐다. 실행 로그에서 MySQL 오류 1062, SQLState 23000 및 아래 메시지를 확인했다.

```text
Duplicate entry '900003' for key 'store.UK2a7h1b2fiymx7vm90mlj2im1q'
```

`SHOW INDEX` 결과 해당 인덱스는 member_id 단일 컬럼에 대한 유니크 인덱스(Non_unique=0)였다. Java의 Store.owner는 ManyToOne으로 변경되어 있었지만, 기존 DB에는 한 회원당 매장을 하나로 제한하는 제약이 남아 있었다. 개발 환경의 ddl-auto=update만으로 기존 유니크 제약 제거까지 보장되지 않음을 확인했다.

### 적용한 조치

외래키 지원용 일반 인덱스를 먼저 추가한 뒤, 확인된 기존 유니크 인덱스만 제거했다.

```sql
CREATE INDEX idx_store_owner ON crm.store (member_id);

ALTER TABLE crm.store
DROP INDEX UK2a7h1b2fiymx7vm90mlj2im1q;
```

이 SQL은 해당 로컬 DB에서 적용한 기록이다. 팀원·배포 DB에서는 인덱스 이름과 기존 일반 인덱스 존재 여부가 다를 수 있으므로 그대로 일괄 실행하지 않는다. [수동 마이그레이션 안내](../sql/store_multi_owner_migration.sql)에 따라 현재 정의를 확인하고 필요한 문장만 실행한다. 적용 후 전체 인덱스 및 외래키 정의도 확인한다.

## 실제 브라우저·MySQL 검증 결과

테스트 매장 ID: 900107. 기존 매장 3개와 연결된 사장님 3명이 있는 상태에서 시작했다.

| 검증 항목 | 실제 결과 |
| --- | --- |
| ADMIN 전체 매장 조회 | 기존 매장 3개의 매장·사장님·이메일 표시 |
| 기존 식당사장에게 테스트 매장 추가 | 등록 성공, 전체 매장 4 / 연결된 매장 4 / 연결된 사장님 3 |
| 적립률 수정 | 같은 ID 900107에서 5% → 10% 변경 |
| 매장명 수정 | 관리자등록확인용 → 관리자수정확인용 변경 |
| 수정 후 집계 | 4 / 4 / 3 유지, 새 매장 행이 추가되지 않음 |
| 소유자 변경 | 식당사장 → 카페사장, 연결 이메일도 새 소유자 이메일로 표시 |
| 새 소유자의 내 매장 정보 | 기존 매장 900101과 변경된 매장 900107이 함께 표시 |
| 새 소유자의 고객 관리 접근 | /customers?storeId=900107 정상 표시, 고객 0명 |
| 이전 소유자의 같은 URL 직접 접근 | 오류 화면 표시, Network의 document 요청 HTTP 403 확인 |

따라서 소유자 변경이 목록 표시뿐 아니라 해당 고객 관리 GET 요청의 서버 소유권 검사에도 반영됨을 확인했다. 모든 API·POST 요청의 권한 검증 완료로 확대 해석하지 않는다.

## 자동 테스트와 남은 확인

- 등록·수정 구현 후 전체 테스트 110건 통과(실패·오류 0). 관리자 테스트는 10건이다.
- H2에서 전체 매장 조회·계정 중복 집계 방지·등록·변경 감지 수정·잘못된 소유자 거절·입력 오류 시 기존 값 유지·404 및 실제 Thymeleaf 출력을 검증했다.
- Controller 권한 분기를 검사했으며 자동 테스트가 실제 보안 필터 전체를 실행한 것은 아니다. 위 브라우저 검증은 실제 로그인 상태의 특정 접근 사례를 보완한다.
- 실제 브라우저에서 입력 오류 메시지·기존 입력 유지, ADMIN 화면·POST의 비관리자 차단, 운영 프로필 화면 및 배포 DB 마이그레이션은 후속 확인 대상이다.
- 테스트 매장 900107은 검증 후 삭제하지 않았으며 최종 확인된 소유자는 카페사장이다.

## 후속 구현: 사장님 계정 목록

- `/admin/owners`를 실제 DB와 연결했다. 현재 사장님 역할인 USER만 표시하고 ADMIN은 제외한다.
- 전체 사장님·매장 보유 사장님·매장 미보유 사장님 수를 표시한다. 매장이 없는 계정도 목록에 포함한다.
- 각 사장님의 소유 매장 목록과 수를 표시하고, 매장 이름으로 관리자 매장 수정 화면에 이동한다.
- 계정 정보는 ID·닉네임·이메일만 조회하며 비밀번호를 조회용 DTO에 포함하지 않는다.
- 미로그인은 로그인으로 이동하고 비관리자는 403으로 차단한다. 신규 계정 생성·계정 정보 수정·승인 상태 관리는 후속 작업이다.
- 로컬 MySQL 브라우저에서 전체 사장님 4명 / 매장 보유 3명 / 미보유 1명, 카페사장 소유 매장 2개와 미연결 계정 표시를 확인했다. 매장 링크에서 900107 수정 화면으로 이동하고 기존 값이 채워짐도 사용자 화면으로 확인했다.

## 후속 구현: ADMIN 사장님 계정 등록

- POST `/admin/owners`: 관리자만 사장님 계정을 등록한다. 현재 사장님 역할 USER를 서버에서 고정하고 역할을 폼 입력으로 받지 않는다.
- 입력값은 이메일·이름·초기 비밀번호이다. 기존 Member의 이메일·nickname 유니크 제약을 유지하며 두 항목 모두 중복 안내를 제공한다.
- 기존 인증의 PasswordEncoder 빈(Argon2)을 재사용한다. 이메일·이름의 앞뒤 공백은 제거하며 비밀번호는 변형하지 않고 해시한다.
- 초기 비밀번호는 8~128자로 검증한다. 일반 회원가입의 기존 최소 길이 정책은 변경하지 않았다.
- 검증 오류 시 이메일·이름은 유지하고 비밀번호를 입력칸에 다시 출력하지 않는다. 동시 등록의 DB 중복 오류는 롤백 후 중복 필드를 재조회해 안내하며, 원인을 확인할 수 없는 DB 오류는 중복으로 숨기지 않는다.
- 새 계정은 소유 매장 0개로 생성된다. 매장 관리에서 기존 또는 신규 매장과 연결할 수 있다.
- H2 및 실제 인코더 테스트에서 USER 고정, 해시 저장과 비밀번호 일치 검사, 이메일·이름 중복, 입력 검증, 오류 화면 비밀번호 미출력, 관리자 권한 분기를 확인했다.
- 실제 MySQL 브라우저에서 계정 900006 생성(전체 5 / 매장 보유 3 / 미보유 2), 이메일 중복·이름 중복의 필드 오류, 일반 입력 유지·비밀번호 비움·계정 수 유지, 생성 시 비밀번호로 로그인 성공을 사용자 화면 및 보고로 확인했다.
- 테스트 매장 900107을 새 계정 900006에 연결한 뒤, 새 계정으로 `/customers?storeId=900107`에 정상 접근함을 확인했다. 이 시점의 소유자는 앞선 카페사장에서 관리자등록사장님으로 변경된 상태다.
- 초기 비밀번호 변경 강제·초대 링크·계정 승인 및 정지는 이번 구현 범위가 아니다.

## 후속 구현: 사장님 이름 수정

- GET `/admin/owners/{ownerId}/edit`에서 기존 이름을 표시하고 POST `/admin/owners/{ownerId}`로 저장한다.
- 수정 입력은 nickname 하나이다. 이메일·비밀번호·역할과 소유 매장 관계는 수정하지 않는다.
- 공백·길이 초과를 검증하고, 자기 현재 이름은 허용하되 다른 계정의 이름과 중복되면 입력값과 필드 오류를 유지한다.
- 없는 계정 및 ADMIN 대상은 404, 비관리자 요청은 403, 미로그인은 로그인으로 이동한다.
- 자동 테스트로 저장·자기 이름 유지·중복 거절·기존 값 보존·화면 출력·대상 및 요청 권한을 검증한다. 실제 MySQL 브라우저에서 이름 수정 및 로그인 후 표시 확인은 후속 확인 대상이다.
