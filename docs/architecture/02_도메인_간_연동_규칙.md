# 도메인 간 계약 및 보안 규칙 v1

1. `auth`가 인증 주체/OWNER의 storeId 조회 계약을 제공한다. `admin`은 매장/계정 관리용 서비스 인터페이스를 통해 `auth`와 협업한다.
2. 다른 도메인의 Repository 직접 호출을 지양한다. 공개 Service/Query DTO 또는 명시적 조회 계약으로 연결한다.
3. ADMIN의 전체 매장 조회와 OWNER의 매장 제한 조회는 별도 권한 경로로 구분한다. 클라이언트가 보낸 storeId를 OWNER 권한 근거로 사용하지 않는다.
4. ADMIN 등록/OWNER 직접 가입은 같은 Member/Store 생성 서비스와 유효성 검사를 재사용한다. 회원가입 시 `ADMIN` 역할 지정 요청은 거부한다.
5. 승인·정지 상태는 인증 이후 매 요청마다 서버에서 검사한다. OWNER가 정지된 매장에 접근하지 못하도록 한다.
6. 방문 기록 + 포인트 적립은 하나의 트랜잭션으로 처리한다. 쿠폰 중복 사용과 포인트 음수 잔액을 막는다.
7. AI는 익명 집계 DTO만 받는다. 민감한 원본 고객 데이터는 AI 요청으로 전달하지 않는다.
8. 공통 파일(`build.gradle`, SecurityConfig, Entity 관계, layout, DB migration) 수정 전 담당자 간 협의 및 PR 리뷰.
9. API 응답: 400 검증, 401 미인증, 403 권한 거부, 404 자원 없음, 409 중복·상태 충돌을 일관되게 사용한다.


## 다중 매장 소유권 원칙 (확정)
- OWNER 1명은 매장 0..N개를 소유할 수 있다. ADMIN의 전체 매장 접근과 구분한다.
- OWNER는 매장 목록 조회 후 활성 매장을 선택한다. 서버는 모든 요청에서 해당 매장의 소유권을 검증한다.
- 매장별 고객·방문·포인트·쿠폰 데이터는 서로 섞이지 않아야 한다.
- 기존 단일 매장 API 응답(`storeId`)과 `/api/stores/me`는 다중 매장용 목록 및 선택 매장 계약으로 재설계해야 하며, 아직 구현된 것으로 간주하지 않는다.
