# 일반 로그인과 Google 로그인 분리

작성자: 김순민 / 작성일: 2026-11-13

## 동작

- `member.provider`가 없거나 공백인 회원은 기존 이메일·비밀번호 인증을 사용한다.
- 제공자가 기록된 소셜 전용 회원은 비밀번호 인증을 허용하지 않는다. DB에 정상 비밀번호 해시가 남아 있어도 같다.
- 일반 폼과 JWT 비밀번호 로그인은 동일한 Spring Security 인증 공급자를 사용한다. `CustomUserDetails.isCredentialsNonExpired()`에서 소셜 계정의 비밀번호 자격 증명을 거부한다. JWT API는 인증 예외를 401로 처리하고 토큰을 만들지 않는다.
- Google 로그인은 Google이 확인한 제공자·고유 ID로 기존 회원을 찾는다. 기존 회원과 이메일만 같다는 이유로 자동 연결하지 않는다. 계정 연결은 별도 본인 확인 정책 없이 제공하지 않는다.
- 신규 Google 회원은 기존 member 테이블에 provider·providerId를 기록한다. 별도 DB나 추가 컬럼은 필요하지 않다.
- Google 측 이메일이 기존 연결과 달라지면 현재 이메일 기반 인증 객체와 불일치하므로 자동 갱신하지 않고 로그인을 거부한다. 이메일 변경은 후속 계정 관리 정책에서 처리한다.

## 기존 데이터와 실행 확인

- 기존 계정의 provider·provider_id를 먼저 확인한다. Gmail 주소라고 해서 Google 가입 계정은 아니다. 이메일 도메인이나 비밀번호 존재만으로 가입 방식을 판별하지 않는다.
- provider가 누락됐거나 과거 일반 계정에 Google 로그인을 자동 연결했던 데이터는 가입 이력을 확인한 뒤 별도 정리한다. 이번 변경에서는 기존 계정·비밀번호·연결 정보를 일괄 수정하지 않는다.
- 브라우저가 비밀번호를 자동 완성하는 현상과 서버가 로그인에 성공하는 것은 다르다. 자동 완성은 브라우저의 저장된 비밀번호를 확인하고 실제 로그인 결과로 차단 여부를 검증한다.
- 서버 재시작 후 Google 회원의 일반 로그인 실패와 Google 로그인 성공, 일반 회원의 기존 로그인 성공을 확인한다. 공용 EC2 DB에서는 먼저 팀에 적용 범위와 기존 계정 연결 정책을 공유한다.

## 자동 검증

- `LoginMethodTest`: 실제 DaoAuthenticationProvider와 해시 비밀번호로 Google 전용 계정 거절, 일반 계정 성공·오류 거절을 검증한다.
- 실제 인증 관리자를 연결한 JWT Controller에서 Google 계정 401 및 토큰 미발급을 확인한다.
- Google 계정 조회·신규 생성·같은 이메일의 일반 계정 자동 연결 차단은 외부 통신 없는 Repository mock으로 검증한다.
- 실제 Google 네트워크 인증·리디렉션, 브라우저 자동 완성, EC2 회원 데이터 정합성은 이 자동 테스트 범위에 포함하지 않는다.

## Google 가입 후 일반 회원가입 중복 차단 (2026-11-13)

- 일반 회원가입은 Google 등 제공자 구분 없이 member 전체에서 이메일 중복을 검사한다. 비교·신규 저장 시 앞뒤 공백과 대소문자를 통일한다. 과거 데이터의 공백·대소문자도 조회 조건에서 비교한다.
- Gmail의 점·플러스 별칭은 이번 정책에서 같은 이메일로 변환하지 않는다. 기존 계정을 삭제하거나 병합하지 않는다.
- Google 신규 회원도 같은 이메일 저장 형식을 사용하고, Google 쪽의 기존 이메일 충돌 검사도 같은 비교 기준을 사용한다.
- 가입 API에 Bean Validation을 적용한다. 중복은 HTTP 409와 Google 로그인 안내 JSON으로 응답한다. 저장은 flush까지 수행하고 DB 제약 충돌도 성공으로 표시하지 않는다.
- DB의 member.email UNIQUE 제약은 계속 필요하다. 이번 변경은 DB 스키마를 변경하지 않는다. 정규화 기준의 동시성 보장은 DB collation·기존 데이터 제약 상태에 따라 별도 확인해야 한다.
- `MemberSignupTest`는 실제 H2에서 Google 계정의 동일·대문자·공백 이메일 재가입 차단, 기존 provider·고유 ID·비밀번호 및 회원 수 보존, 일반 계정 중복, 정상 신규 저장·해시, API의 409/400 응답을 검증한다. MockMvc는 standalone이므로 실보안 필터 검증을 대신하지 않는다.
- 추가 테스트 후 전체 155건 통과(실패·오류 0)를 확인했다. 실제 EC2 DB에서 보고된 재가입 현상의 직접 원인은 아직 확정하지 않았다. 재시작 후에도 재현되면 요청 응답·실제 연결 DB·저장된 이메일·유니크 제약을 대조한다.
