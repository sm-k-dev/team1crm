# 고객 삭제 및 주요 정보 제거 정책

확인일: 2026-11-11 / 작성자: 김순민

## 처리 흐름
- 삭제 요청 즉시 Customer.deletedAt을 기록하고 일반 고객 목록·검색·건수·상세·수정에서 제외한다.
- 삭제 시각에서 달력 기준 3개월이 지나면 일일 배치가 주요 고객 정보만 제거한다. 고객 행 영구 삭제 계획을 이 정책으로 대체한다.
- 이름은 ‘삭제된 고객’, 전화번호·생일 월·메모는 NULL, 마케팅 동의는 false로 바꾸고 anonymizedAt을 기록한다.
- 고객 ID·매장 관계·생성일·삭제일과 방문·포인트·쿠폰 기록은 보존한다. anonymizedAt이 있는 고객은 다시 처리하지 않는다.

## 배치 활성화와 날짜 기준
- 기본 시각: 매일 오전 03:00, Asia/Seoul. 스키마 적용 전 오실행을 막기 위해 기본 비활성이다.
- 마이그레이션 후 CUSTOMER_PRIVACY_ENABLED=true로 설정하고 앱을 재시작한다.
- CUSTOMER_PRIVACY_CRON으로 예약 시각을 변경할 수 있다. 기본값: 0 0 3 * * *.
- TIMESTAMPADD(MONTH, 3, deleted_at) <= 처리시각으로 판정한다. 90일 또는 단순 처리일-3개월 기준을 사용하지 않는다.
- 예: 2026-11-30 03:00 삭제 → 2027-02-28 03:00 만료. 월말·윤년을 달력 기준으로 보정한다.
- 단일 조건부 UPDATE로 정보 제거와 완료 시각을 함께 기록한다. 이미 완료된 행은 재실행 시 제외한다. 실패하면 롤백하고 다음 예약 실행에서 재시도한다.
- 대량 운영 데이터에서는 실행 시간·잠금·인덱스를 확인하고 청크 처리·실행 건수 모니터링을 추가한다.

## DB 변경과 번호 재사용
- docs/sql/customer_privacy_migration.sql을 제공한다. 자동 실행하지 않으며 백업 후 현재 컬럼을 확인하고 필요한 문장만 적용한다.
- deleted_at·anonymized_at nullable DATETIME 컬럼과 phone의 nullable 변경이 필요하다.
- dev ddl-auto=update에만 의존하지 말고 SHOW COLUMNS로 실제 phone NOT NULL 제약 해제를 확인한다. 운영 validate는 스키마를 변경하지 않는다.
- 기존 (store_id, phone) 유니크 제약은 유지한다. 보관 중에는 같은 번호 재등록을 막고, NULL 제거 후에는 기존 번호 재등록을 허용한다. MySQL은 유니크 제약에서 여러 NULL을 허용한다.
- 활성 고객의 전화번호 필수 검증은 Form·Service가 유지한다.

## 통계와 고객 업무
- 과거 매출·방문 건수·고유 방문 고객 수에는 삭제 고객의 이력을 포함한다. 고객 ID가 보존되므로 기존 고객 JOIN을 유지할 수 있다.
- 현재 고객 대상 RFM은 deleted_at IS NULL로 제외한다. AI·마케팅도 동일 원칙으로 연동한다.
- 신규 방문·포인트·쿠폰은 CustomerService.findCustomer 등 삭제 고객을 거부하는 업무 조회를 사용한다.
- 전체 엔티티 일괄 필터는 과거 통계를 바꿀 수 있으므로 사용하지 않는다. 기본 JpaRepository 조회·삭제 메서드는 업무 조건을 자동 적용하지 않으므로 직접 사용에 주의한다.
- 매장 자체 삭제 시 CASCADE 정책은 이번 변경 범위 밖이다.

## 범위와 검증
- 제거 대상은 customer 테이블의 이름·전화번호·생일 월·메모·수신 동의이다.
- 고객 ID·상세 이력이 남으므로 완전한 익명화를 보장한다고 표현하지 않는다. anonymizedAt은 주요 정보 제거 완료 시각이다.
- 방문 메뉴 메모·쿠폰 제목·로그·내보낸 파일 등 다른 곳에 복사된 개인정보는 별도 점검 대상이다. 자유 입력 개인정보 처리 범위는 C·D·인프라 담당과 확인한다.
- H2 통합 테스트: 달력 3개월·월말·윤년 경계, 활성 고객 제외, 여러 NULL 번호, 재처리 제외, 고객/방문/포인트/쿠폰 및 과거 매출·고유 방문 고객 수 보존.
- 로컬 MySQL 스키마 변경·배치 실행·테스트 고객의 과거 집계 보존은 아래 수동 검증에서 확인했다. 분석 화면의 수치 대조와 운영 환경 적용은 별도 확인 대상이다.

## 로컬 MySQL 수동 검증 기록

검증일: 2026-11-11 / 수행자: 김순민 / 기록 근거: 사용자 실행 결과 및 공유한 브라우저·Workbench 화면

### 환경과 준비
- 로컬 개발 앱(localhost:8082)과 MySQL의 crm 스키마, 매장 ID 900101에서 수행했다.
- 앱 재시작 후 deleted_at·anonymized_at 생성은 확인했으나 phone의 Null은 NO였다. `ALTER TABLE crm.customer MODIFY COLUMN phone VARCHAR(13) NULL;` 실행 후 세 컬럼 모두 Null=YES임을 확인했다.
- 배치 실행 전 전체 처리 대상 조회로 해당 테스트 고객 한 명만 대상임을 확인했다.
- 테스트할 때만 Program arguments에 아래 설정을 추가하여 앱의 실제 스케줄러·서비스를 실행했다. 개인정보 제거 UPDATE를 Workbench에서 직접 실행한 검증이 아니다.

```text
--app.customer.privacy.enabled=true --app.customer.privacy.cron="*/10 * * * * *"
```

### 거래 이력이 있는 고객의 과거 집계 보존
테스트 고객: ID 900233, 매장 ID 900101, 이름 ‘집계보존확인용’.

- 검증용 방문을 SQL로 2건 생성했다. 방문 시각/금액은 2026-11-10 10:00:00 / 10,000원과 2026-11-11 11:00:00 / 20,000원이다. 방문 INSERT는 포인트 적립 등 방문 등록 서비스의 로직을 실행하지 않는다.
- 화면에서 소프트 삭제 후 집계를 비교했다. 이후 이 고객의 deleted_at만 4개월 전으로 변경하고, 전체 처리 대상이 이 고객 한 명임을 확인한 뒤 앱 배치를 실행했다. 방문 시각은 변경하지 않았다.

| 시점 | 방문 수 | 매출 합계 | 고유 방문 고객 수 |
| --- | ---: | ---: | ---: |
| 삭제 전 | 2 | 30,000원 | 1 |
| 소프트 삭제 후 | 2 | 30,000원 | 1 |
| 주요 정보 제거 후 | 2 | 30,000원 | 1 |

배치 실행 후에도 고객 ID·매장 ID와 방문의 연결이 유지됐다. 이름은 ‘삭제된 고객’, phone·birth_month·memo는 NULL, agree_marketing은 0이었으며 anonymized_at=2026-11-11 12:39:00.010335가 기록됐다.

세 시점에 동일하게 실행한 집계 조회:

```sql
SELECT
    COUNT(v.id) AS visit_count,
    COALESCE(SUM(v.amount), 0) AS revenue,
    COUNT(DISTINCT v.customer_id) AS unique_customer_count
FROM crm.visit v
JOIN crm.customer c ON c.id = v.customer_id
WHERE c.store_id = 900101
  AND c.id = 900233
  AND v.visited_at >= '2026-11-01 00:00:00'
  AND v.visited_at <  '2026-12-01 00:00:00';
```

과거 집계에는 c.deleted_at IS NULL 조건을 넣지 않는다. 이번 결과는 해당 테스트 고객의 2026년 11월 SQL 집계 보존을 확인한 것이며, 분석 화면 전체 검증을 대신하지 않는다.

### 테스트 설정 정리 및 남은 확인
- 첫 번째 배치 검증 후 사용자가 테스트 실행 인자를 제거하고 서버를 정상 재시작했다고 확인했다.
- 거래 이력 검증을 위해 두 번째로 켠 10초 주기 설정은 검증 후 제거하도록 안내했다. 두 번째 실행 이후 제거·재시작 완료 여부는 추가 확인이 필요하다.
- 실제 MySQL에서 포인트·쿠폰 이력 보존, 분석 화면 수치 대조, RFM 제외, 월말·윤년 경계 및 운영 환경 적용은 이번 수동 검증 범위에 포함하지 않았다. H2 테스트와 실제 MySQL 수동 검증의 범위를 구분한다.
