# 개발/운영 환경 및 DB 정책

**현재 Starter는 MySQL(DataSource/JPA)과 Thymeleaf가 활성화되어 있습니다.** 기본 프로필은 `dev`이며, `dev`와 `prod` 모두 접속 가능한 MySQL이 필요하고 `spring.thymeleaf.enabled=true`로 설정되어 있습니다. Thymeleaf 캐시는 개발에서 비활성화, 운영에서 활성화됩니다. 업무 Controller와 SecurityConfig의 인증·인가 코드가 구현돼 있습니다. 코드 존재와 실제 운영 검증 완료는 구분합니다. 전체 실행 변수는 [README](../README.md)의 환경변수 표를 확인합니다.

기술 기준: **JDK 25, Spring Boot 4.0.0, Gradle 9.2.1, MySQL 8**.

## DB 연결형 로컬 개발(dev)
1. MySQL에 `crm` 데이터베이스와 개발 전용 사용자를 생성합니다.
2. `SPRING_PROFILES_ACTIVE=dev`, `SERVER_PORT`(예: `8082`), `DB_USERNAME`, `DB_PASSWORD`를 실행 환경변수로 지정합니다. URL이 다르면 `DB_URL`을 지정합니다. `.env` 파일은 자동으로 로드되지 않으므로 IDE 또는 운영체제 환경변수로 주입합니다.
3. Windows PowerShell에서 `.\gradlew.bat bootRun`을 실행하거나 IntelliJ에서 `CrmApplication`을 실행합니다. 프로필은 환경변수 한 곳에서 지정합니다.
4. `ddl-auto=update`: 기존 데이터를 지우지는 않지만 스키마 변경을 안전하게 보장하지 않습니다. 변경 전 백업하세요.
5. SQL 자동 실행은 꺼져 있습니다. 현재 시연 데이터는 dev에서 `CRM_DEMO_ENABLED=true`와 공통 정책을 만족하는 `CRM_DEMO_PASSWORD`로 한 번 생성합니다. 생성 후 플래그를 끕니다. [통합 기준](architecture/14_요구사항_통합_수정_20261123.md)을 따르며, 과거 [seed_dummy.sql](sql/seed_dummy.sql)은 선행조건을 확인할 별도 개발 자료입니다.

## 운영(prod)
1. `deploy/crm.env.example`을 서버의 `crm.env`로 복사하고 비밀번호/키를 채우며 `chmod 600` 적용.
2. `crm.env`에 `SPRING_PROFILES_ACTIVE=prod`를 지정합니다. systemd 서비스는 `EnvironmentFile`로 이 파일을 읽습니다.
3. `SERVER_PORT`, `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` 필수. **운영 DB는 스키마가 사전에 준비되어야** 합니다.
4. `ddl-auto=validate`: 기존 스키마를 검사만 하며 생성/변경하지 않습니다. 엔티티와 불일치하면 앱이 시작되지 않습니다.
5. `spring.sql.init.mode=never`: SQL 초기화 스크립트 자동 실행을 끕니다. 별도 Java 생성기인 FakeDataInitializer는 dev 프로필과 활성화 플래그 조건에서만 등록되며 prod에서는 시연 데이터를 생성하지 않습니다.
6. 변경 전 DB 백업, 별도 SQL 마이그레이션을 승인·적용한 뒤 배포. 이후 Flyway 도입 권장.

## 테스트
H2 의존성과 테스트별 인라인 DB 설정을 사용하는 자동 테스트가 있습니다. 테스트의 프로필·속성·mock 범위는 각 클래스를 확인합니다. prod MySQL 검증처럼 별도 실행 조건이 있는 테스트도 있으므로 H2 통과를 전체 운영 환경 검증으로 확대하지 않습니다. 실행 명령과 결과 위치는 [README](../README.md)를 참고합니다.

## 기존 DB의 다중 매장 제약 확인
- 기존 사장님에게 두 번째 매장을 등록할 때 member_id 중복 오류가 발생하면 [다중 매장 마이그레이션 안내](sql/store_multi_owner_migration.sql)를 확인합니다.
- `ddl-auto=update`가 기존 유니크 제약을 제거한다고 가정하지 않습니다. 인덱스와 외래키를 확인하고, 일반 인덱스를 유지한 상태에서 member_id 단일 컬럼 유니크 제약만 제거합니다.
- 실제 오류 원인과 조치·등록·수정·소유자 변경 검증 결과는 [ADMIN 매장 관리 검증 기록](architecture/08_ADMIN_매장_관리_검증.md)에 정리했습니다.

## 중요 제한
- 승인·반려·정지·재활성화는 현재 제출 범위에서 제외합니다. ADMIN의 사장님 계정 등록·이름 수정·매장 관리 코드는 구현돼 있으며 승인 상태 관리와 구분합니다.
- 주요 업무 화면 Controller는 `@Profile({"dev", "prod"})`로 두 프로필에서 등록됩니다. 미리보기 보안 설정과 시연 데이터 초기화는 `dev` 전용이며, 운영에서는 실제 보안 설정·DB·외부 연동을 검증합니다.
- 빌드·테스트 결과는 실행 시점과 환경별 기록을 따릅니다. 과거 통과 기록이 최신 운영 DB·외부 연동·브라우저 검증 완료를 뜻하지 않습니다.
- 운영 DB를 빈 상태에서 시작하면 `validate`가 실패하는 것이 정상입니다. 테이블을 먼저 생성/마이그레이션해야 합니다.
